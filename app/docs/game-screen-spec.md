# ゲーム画面仕様・設計メモ

更新日: 2026-10-18（日本時間）

ユーザーとの仕様確認結果と実装方針をまとめる。初期実装と検証状況は [game-screen-validation.md](game-screen-validation.md) を参照。
「確定仕様」はユーザーの回答、「実装方針」はその仕様を実現するための設計判断を記載する。

## 1. 確定仕様

### 対象と担当

- iPhone / iPad向けのARゲーム。プレイ人数は2人固定。
- ホストは `personalEvidences`、ゲストは `physicalEvidences` を担当する。
- 各端末が独立したAR空間に証拠を配置する。AR空間・Entityの座標は端末間で共有しない。
- 現行エピソードは各担当6件、合計12件。表示・判定にはデータの件数を使い、6 / 12を固定値にしない。
- 画面はMVVM、ARの処理はRealityKitのECSで設計する。

### フェーズと今回の実装範囲

```text
ロビー（ホストが推理開始）
  → opening
  → AR調査
  → ending
  → ゲームクリア
```

- `GamePhase` により、ARと全画面のUIをシステムが切り替える。
- フェーズ用の全画面UIはスワイプ・閉じる操作などで任意に解除できない。
- openingはホストの操作で2人同時に進める。ゲストが独立して進めることはできない。
- 今回のopeningは開始用の仮画面。ホストの開始操作で2人がAR調査へ進む。
- 今回のendingは人物・証拠の選択と正誤判定まで実装する。
- opening / endingの台詞表示、演出、ストーリーの本格的なUIは後回し。
- 証拠詳細の「村人に話を聞く」はボタンの表示まで。中身は未実装でよい。

### ARへの配置

- アプリが条件を満たした証拠から順次自動配置する。プレイヤーによる配置操作は不要。
- 各証拠の `classification` と認識した面の分類が一致することが必須。
- 分類を認識できない・配置可能な面が足りない場合は待機し、条件を緩めない。
- 同一端末内の証拠モデルの中心間を、3D距離で1m以上離す。
- 壁面への配置の高さは制限しない。認識した壁面の範囲内を使う。
- 現在のJSONは全証拠が `Wall`。名称から床・机などへ独自に読み替えない。
- 最初は約10cm角の札状の仮モデルを壁面に沿わせ、証拠名を表示する。
- 実モデルは後から差し替えられるようにし、証拠ごとのサイズ・向きを設定可能にする。
- 収集後もEntityを残す。残っている収集済みEntityも1m間隔の判定対象に含める。

### AR画面と撮影

| 状態 | AR表示 | 操作 |
| --- | --- | --- |
| 探索 | 縦長9:16 | 証拠ボタン、撮影開始ボタン |
| 撮影 | 正方形1:1 | シャッターボタン、左側にキャンセルボタン |

- 撮影開始時は証拠未選択で、シャッターボタンは無効。
- 撮影モードで画面内の証拠Entityをタップして選択する。
- 選択した証拠が画面内にあり、カメラからモデル表面までの距離が30cm以内の間だけ撮影できる。
- 距離超過・画面外などで条件から外れたら選択を解除する。条件内に戻っても再タップが必要。
- キャンセルで撮影モードを終了し、探索画面へ戻る。
- 保存する画像は、現実のカメラ映像とARモデルを含む1:1画像。操作ボタンなどのUIは含めない。
- 写真の保存に成功して初めて、その証拠を収集済みにする。
- 撮影成功後はEntityを残し、探索画面へ戻る。
- 再撮影を許可する。写真は最新の1枚に置き換え、収集件数を増やさない。
- 探索・撮影の両方で、右上に「自分の収集済み / 自分の全件」と「2人の収集済み合計 / 全件」を表示する。

### 証拠モーダルと写真

- 証拠ボタンからモーダルを開く。
- 自分が撮影済みの証拠だけを表示する。未収集・相手の証拠は一覧に出さない。
- 各証拠には小さめの撮影写真、`description`、村人に話を聞くボタンを表示する。
- 写真は撮影した端末内で保持し、相手へ送らない。
- 撮影写真は同一ゲームの再同期や通信復帰によって消えない。

### endingと正誤判定

- 2人が担当する全証拠を収集すると、自動で `ending` に移行する。
- 自分の担当分だけを集め終わっても、相手の完了まではAR調査を続けられる。
- ホストが2人共通の提示先の人物を1人選択し、確定する。
- その後、各プレイヤーが自分の担当証拠を1つ選択し、確定する。
- 2人の証拠が揃った時点で判定する。
- 正解条件は、共通人物が `keyPersonID`、ホストの証拠が `keyPersonalEvidenceID`、ゲストの証拠が `keyPhysicalEvidenceID` に一致すること。
- 人物ID 0のナレーションは提示先から除外する。
- すべて正しければ2人ともゲームクリアへ進む。
- 誤答は何度でも再挑戦できる。失敗したら共通人物と両者の証拠選択をリセットし、2人とも選び直す。
- 本文の推理上の意味から独自に正解を変更せず、JSONの正解IDを判定に使う。

### 通信切断と再開

- ゲーム中に切断したら、進行と操作を一時停止する。
- フェーズ、収集済み情報、撮影写真を保持する。
- 同じ相手との再接続・状態同期が完了したら再開する。
- 保証範囲は、2人ともアプリを終了していない間の通信切断・復帰まで。
- アプリ終了・プロセス終了後のゲーム復元は今回の範囲に含めない。

## 2. 実装方針

### 状態の分離

| 状態 | 所有・同期方針 |
| --- | --- |
| エピソード / ゲームデータ | 既存のEpisodeManagerで保持 |
| ゲームフェーズ / 共通人物 / 両者の提出 / 判定結果 | GameManagerで管理し、ホストを確定状態の管理者とする |
| 収集済みフラグ / 各カウント | ホストが担当・証拠IDを検証して更新し、2人へ同期 |
| 探索 / 撮影 / モーダル / 選択対象 / 撮影処理中 | 端末ごとの画面状態として管理 |
| 写真 | 端末内だけで保持。共有するGameStateにUIImageを含めない |
| Entity / ARアンカー / 配置位置 / カメラ位置 | 端末ごとのAR実行環境で保持し、通信しない |
| 接続待機 / 再同期中 | GamePhaseとは別に管理し、操作を遮断 |

- `GamePhase` は `.opening` / `.investigation` / `.ending` / `.cleared` を想定する。
- AR内の状態は別の型で `.exploring` / `.photographing` を表す。
- 証拠IDは人的・物的の間で重複するため、`EvidenceKind + Int` の不変の識別子を用意する。
- 写真の辞書キーにもこの識別子を使う。`isCollected`などが変わるEvidence全体をキーにしない。
- 同一ゲームの識別には `GameData.id` を利用し、別ゲームの操作や状態と混同しない。
- opening / endingはGamePhaseから全画面表示を導出する。UIを閉じた事実でフェーズを変えない。
- AR表示枠の9:16 / 1:1切り替えでARView・ARSessionを作り直さない。

### MVVMとECSの責務

| 要素 | 責務 |
| --- | --- |
| GameView / 各画面View | フェーズに応じた描画、モーダル、操作入力 |
| GameViewModel | 表示値と操作受付。GameManagerとAR出力を画面状態へ反映 |
| GameManager | フェーズ、収集の反映、共通人物、提出、正誤判定、再同期の調整 |
| EpisodeManager | エピソードとゲームデータ、端末内写真の取得・保存窓口 |
| PeerManager | 相手との接続、メッセージ送受信。正誤判定を持たせない |
| AR用のViewブリッジ / 実行環境 | ARViewとARSessionの保持、ARKit入力、タップ入力、スナップショットの取得 |
| Component | 証拠の識別・配置条件・選択・収集・撮影要求などのデータ |
| System | 配置候補の評価、間隔の検証、選択と撮影可能条件の継続判定、撮影要求の処理 |

- 平面・カメラ・タップ情報はARKit / UIKitのブリッジからECSへ渡す。
- AR上の配置・距離判定をViewModelやCoordinatorへ集中させない。
- Systemから出る「選択変更」「撮影可否」「撮影要求」などを画面・保存処理へ渡す。
- 写真取得自体はARViewの機能をブリッジ経由で呼び出す。AR描画と別のAVCaptureSessionを同時に起動しない。
- SwiftUIの状態更新と共有ゲーム状態への反映はMainActorに集約する。

想定する最小構成:

- `EvidenceComponent`: 証拠の種別・ID、必要なclassification、配置設定。
- 配置・選択・収集状態のComponent、およびカメラ入力・タップ入力・撮影要求のデータ。
- `EvidencePlacementSystem`: 認識面と間隔を検証し、条件を満たす証拠を配置する。
- `EvidenceSelectionSystem`: タップ対象の解決と、距離・画面内表示・追跡状態による選択解除。
- `EvidenceCaptureSystem`: 撮影要求時の再検証、二重要求の抑止、撮影結果との対応付け。

型名と分割粒度は実装時に調整するが、上記の責務は維持する。

### 配置・撮影の整合性

- モデル中心は証拠ルートの配置基準点に統一し、モデルやラベルの原点差で間隔が変わらないようにする。
- classification機能自体が非対応の場合は配置できない理由を表示し、対応する面が未発見の場合と区別する。分類条件を緩めて代替配置しない。
- 30cm判定は証拠モデル本体の表面を基準にし、ラベル・選択表示の境界を距離に含めない。
- 仮の札はその形状から表面距離を算出する。実モデルへの差し替え時も中心距離で代用しない。
- 1:1の表示枠に合わせて画面内判定と保存画像を揃える。
- 平面の更新・統合後も配置条件を検証し、不正な配置を有効な証拠として扱わない。
- シャッター受付時にも条件を再確認する。撮影失敗で収集済みにしたり、既存写真を消したりしない。
- 撮影中の多重タップ、別ゲーム・別フェーズへ移った後の古い撮影コールバックを反映しない。
- キャンセル、フェーズ遷移、通信待機によって撮影操作を中断した場合は選択を解除する。

### 同期と再接続

- ホストのゲーム開始をゲストへ通知し、ゲストの画面もゲームへ遷移させる。
- 参加者は1人だけ受け付け、ゲーム開始後は同じ相手だけが復帰できるようにする。
- ゲストは操作要求を送り、ホストが現在のフェーズ・役割・証拠を検証して確定状態を配信する。
- ホスト自身の操作も同じ更新ルールを通す。
- 収集は証拠ごとに一度だけ加算する。再撮影・再送で件数が増えないようにする。
- 写真保存済みだが未確認の収集要求を区別し、通信復帰時に再照合する。
- メッセージID、状態の版、endingの試行番号により、重複や前回の提出を再適用しない。
- 人物の確定後はその試行中の人物を固定し、2人の提出を同じ試行に紐づける。
- 2人の全証拠収集をホストが検知するとendingを配信する。開いていた証拠モーダル・撮影画面よりフェーズ切り替えを優先する。
- 再接続時はホストの共有状態と、ゲストの未確認操作を照合してから操作を再開する。端末内写真や既存AR配置を初期化しない。
- ARの追跡が一時的に失われた場合も撮影を無効化し、追跡回復を待つ。追跡不能中に配置条件を満たしたことにしない。

### UIの細部に関する初期方針

以下は追加質問を必要としない初期実装上の判断。実機で確認して調整する。

- 撮影画面はシャッターとキャンセルを主操作にし、証拠モーダルは探索画面から開く。
- 証拠が0件ならモーダルに未収集の案内を表示する。
- 村人に話を聞くボタンは未実装と分かる無効状態で置く。
- 収集済みの札には収集済み表示を付けるが、再撮影のタップ対象には残す。
- 一度確定した自分の提出は待機表示にし、その試行が終わるまで変更しない。
- clearは結果表示まで用意し、今回のストーリー演出には含めない。

## 3. 既存コードから必要になる変更

- `ContentView` の `.Game` は現在TitleViewのため、GameViewへ接続する。
- `ContentView` とViewModelでEpisodeManagerの参照先が分かれないように揃える。
- 現在のGameStateにはフェーズ・提出などがないため、必要な共有状態を追加する。
- 仮の `PlayerAction.acquireItem(id: String)` を役割と証拠種別が明確な操作へ変更する。
- PeerManagerの受信元・ホスト判別、2人制限、同じ相手への再接続、プレイヤー重複登録を整える。
- 現在のCameraManagerは単独のAVCaptureSessionを使うため、AR写真にはARView側の撮影経路を使う。
- `EpisodeManager.resources` のキーと写真アクセス方法を整える。
- JSONのビルド時警告があるため、実機でBundleから正常にロードできることを確認する。
- StoryDataの既存タグとGamePhaseの詳細な対応付けはストーリーUI実装時に行う。結果用ストーリーID 3は現在のEpisodeDataのstoriesに含まれていない。

## 4. 実装順序と確認事項

1. 証拠の識別子、GamePhase、共有状態、GameManagerの更新・判定ルールを作る。
2. ホストの開始・収集・endingの同期と、切断・再接続時の操作制御をつなぐ。
3. GameView、opening仮画面、ARの探索 / 撮影UI、証拠モーダルの枠を作る。
4. RealityKit ECSで仮モデルの分類別自動配置、間隔、選択、表面距離判定を実装する。
5. AR写真の取得・保存・再撮影と、収集済み反映をつなぐ。
6. endingの共通人物選択、両者の提出、誤答時リセット、clear表示を実装する。
7. 実機2台で通し確認する。

共有状態のテストでは、役割外の操作拒否、収集の重複、全件収集時の遷移、両者提出待ち、正誤判定、前回試行の提出排除、再接続での状態維持を確認する。

実機では、壁のclassification待機、実寸1m間隔、表面まで30cmの判定、画面外での選択解除、表示枠変更によるAR継続、UIなしの1:1写真、再撮影、証拠モーダル中のending移行、通信復帰を確認する。

画面のビルド成功だけでAR条件と2台間の同期を検証済みとしない。
